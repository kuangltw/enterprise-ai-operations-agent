# ADR M2-01：未完成上傳的儲存鍵輪替

日期：2026-11-15。狀態：推薦方案 B，正式實作基準待獨立審查。

## 問題與現有約束

上傳回應不明或失敗後，舊 PUT 仍可能寫入原鍵。新世代以不同實體鍵隔離後續有效版本。0011 的 `protect_document_version_identity` 會拒絕更新 `document_versions.storage_key`，版本的非空複合外鍵又固定要求同租戶、文件、版本、世代的 `live` 鍵。仍被參照的鍵無法退役，Registry 亦會保留所有永久鍵與其版本歸屬。 [0011 資料結構](../database/SCHEMA.md#8-鍵登錄實作狀態migration-0011_document_key_registry) · [儲存安全實證](../testing/M2-01-STORAGE-SAFETY-PROOF.md)

## 方案比較

| 考量 | A．新增文件版本 | B．同版本受控原子換鍵 |
| --- | --- | --- |
| 版本與 API | 保留歷史列及原鍵。新版本 ID 與版本號會影響同一冪等鍵重試的 202 回應及 `latest_version`。若當作同一上傳，須新增請求對嘗試版本的映射。 | 固定文件 ID、版本 ID、版本號、SHA-256、內容與冪等鍵。儲存鍵是內部欄位，既有 API 可沿用。 |
| 發布、ACL、索引 | 文件層 ACL 可延續。須重驗授權、建立不可發布的替代狀態、定義舊引用語意，並跨版本防止重複索引。 | 文件層 ACL 與現有索引 Job 唯一鍵沿用。同一版本可能已有讀者、索引或歷史引用，因此僅適用於從未成功儲存、發布或索引的版本。 |
| 退役與遷移 | 0011 仍要求原版本引用 `live` 鍵。若須同時保留原版本及退役原鍵，必須新增歷史鍵參照及禁止原版發布的規則。 | 需新增角色限定的換鍵入口與持久操作表，並讓各寫入入口共同核對世代。新鍵先登錄，版本先切換，再退役原鍵，繼續使用 0011 外鍵。 |
| 成本與用途 | 適合真正新增內容版本。用於失敗上傳恢復，會擴大版本、引用與 API 語意的變更。 | 適合以相同內容恢復未成功的上傳，授權與交易複雜度集中在內部受控入口。 |

Architect 前置審查推薦 **B：受控原子換鍵**。僅處理同一 PDF 內容、文件有效、從未儲存成功或對外發布、索引狀態為 `pending` 且無任何索引工作的 `pending_upload`／`failed` 版本。無法證明從未發布，或仍有任何有效引用時，拒絕輪替。內容變更走產品的新版本流程。 [既有上傳契約](../api/CONTRACT.md)

## 資料模型與安全不變條件

- 版本的 id、租戶、文件、版本號、內容摘要及上傳冪等鍵保留。複合外鍵保證目前版本始終持有正規且歸屬完全吻合的 `live` 鍵。新鍵使用 UUID 世代，世代無時間順序。
- Registry 保留每個鍵，原鍵只能由 `live` 轉 `retired`。操作表以 `(tenant_id, operation_id)` 識別，對原 namespace／key 設唯一約束，保留文件、版本及原新世代。舊鍵外鍵要求 `retired`，新鍵外鍵只綁定永久身分，以支援後續換鍵及重播歷史結果。
- 專用 `NOLOGIN`、非表擁有者、非 Superuser 角色持有受控函式。函式固定 `search_path`、限定 schema 且撤銷 PUBLIC EXECUTE。版本身分 Trigger 持續作用，只有該角色的受控入口可變更儲存鍵。執行角色無直接 DML 或切換為函式擁有者的權限。正式上線前須驗證實際角色、整表與欄位授權、函式擁有權及不可繞行的發布／索引入口。

## 交易、鎖序及復原

原型用真實隔離 DB 登入綁定合成租戶。取得授權範圍鎖後，換鍵先取租戶／操作 ID 的 Advisory Lock（建議鎖），再依序鎖文件、版本、原 Registry 鍵，重驗狀態與索引工作。完成入口採用相同的文件、版本及原鍵順序，並驗證呼叫者攜帶的預期世代。READ COMMITTED 下等待後用新 SQL 讀取。

同一交易依序登錄新 live 鍵、比對原鍵與世代後更新版本、退役原鍵、寫入 `waiting_fence` 操作結果，任一步失敗即回滾。先切換參照才可退役，因為 Registry 外鍵的 `ON UPDATE RESTRICT` 立即檢查。交易沒有物件儲存 I/O。 [PostgreSQL 16 CREATE TABLE](https://www.postgresql.org/docs/16/sql-createtable.html)

相同操作 ID、相同輸入回傳原結果，即使原結果的新鍵後來已退役。相同操作 ID 配不同輸入拒絕，第二個操作 ID 也不能再次輪替相同舊世代。COMMIT 回應不明時，透過 authoritative primary（權威主庫）的新連線，以原操作 ID 等待原交易結束並重查，確認不存在才以相同 ID 重試。歷史結果不可作為現行儲存鍵或發送 PUT 的授權。

正式設計還需要 schema gate、有效身分／租戶／成員／ACL、文件上傳冪等鍵、換鍵操作 ID、文件、版本、Registry、寫入嘗試及索引工作的全入口鎖序。授權與鎖後檢查通過才可切換。PUT 前先提交綁定原鍵、世代及 attempt ID 的寫入意圖。完成、失敗、索引或發布均需在鎖內重驗授權，並比對嘗試識別、鍵與世代。使用長期固定的 generation／attempt 最後活動時間判定資格，避免換鍵後沿用版本建立時間立即再次成為候選。

## Migration 與驗收

保留既有 0011。正式能力需獨立的前向 Migration，部署前盤點舊執行角色的整表授權、未受管理的寫入、歷史發布與索引紀錄、墓碑與存量、不相容資料、鎖定與執行時間。停寫並清退舊 API／Worker 後再調整 Schema 及授權，使用代表性資料驗證 Migration、故障回滾、備份還原及主庫切換。0011 的禁止降版政策仍適用。

| 驗證 | 證據範圍 |
| --- | --- |
| 實際 0011 上的 B 原型 | **14 項通過，0 跳過。** 新鍵與不可逆墓碑、版本及 ACL 身分保留、租戶／文件／版本／世代錯配、同鍵等待及鎖後拒絕、相同操作重試、回滾、真實 COMMIT 回應遺失、舊世代完成拒絕與索引防重。原型要求 `current_version IS NULL`，完成入口用合成資料模擬已驗證內容。尚未涵蓋有其他已發布版本的文件、歷史發布證據、已持久化的上傳嘗試及原型 COMMIT 前斷線。 |
| 0011 專項 | **29 項本機通過，0 跳過。** 0010 預覽／並行 9 項、既有資料升級／拒絕 9 項、空庫升級後的鍵約束／PDF／ACL 11 項。測試套件固定直接與轉接版本；尚未固定各 wheel 的雜湊。GitHub Actions 待遠端執行。 |
| 正式應用層待驗 | 現行完成入口依冪等鍵重新取當前鍵，完成／失敗更新缺少世代條件，且資料庫持鎖跨 MinIO I/O。須先部署受控的世代／attempt 邊界與共用鎖序，測試 ACL 撤銷、相容版本切換、舊請求、發布及索引入口。原型固定登入的租戶範圍不涵蓋正式授權。 |
| 資料面待驗 | 排空單 PUT、multipart、緩衝、重送、舊 worker 和特權寫入，驗證正式租戶隔離、可信 cluster／bucket incarnation、墓碑復原及刪除授權／對帳。 |

重跑 0011 專項使用 `python scripts/testing/run_key_registry.py --pull`，換鍵原型使用 `python scripts/testing/run_key_registry.py --pull --rotation`。兩者使用合成資料與一次性服務。PDF／ACL 回歸執行於原版 0011，驗證既有流程。正式 API 換鍵後的 PDF 端到端流程待後續接線。
